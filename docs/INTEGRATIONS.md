# Интеграции и API-ключи: что, где взять и куда вносить

Есть два способа задать доступы:

1. **Через интерфейс (рекомендуется)** — раздел **«Настройка → Интеграции»** в дашборде.
   Там можно ввести токены/вебхуки, переключить источник данных (демо ↔ боевой) и
   **проверить подключение** к каждому сервису с отображением статуса — без правки `.env`.
   Значения сохраняются в БД и применяются поверх переменных окружения (в т.ч. после
   перезапуска). Секреты в интерфейсе показываются замаскированными; пустое поле секрета
   при сохранении не затирает уже сохранённое значение.
2. **Через `.env`** — базовые значения по умолчанию (используются, пока их не переопределили
   в интерфейсе). Шаблон со всеми переменными и комментариями — `.env.example`.

После изменения `.env`:
```bash
docker compose -f docker-compose.prod.yml up -d      # применить
docker compose -f docker-compose.prod.yml exec api python -m app.services.ingest   # выгрузить
```

Пункты, отмеченные **«!»**, оформляются заранее — одобрение занимает время.

| Интеграция | Переменные в `.env` | Где получить | Права/примечания |
|---|---|---|---|
| **Битрикс24** | `BITRIX24_WEBHOOK_URL`, `BITRIX24_INBOUND_TOKEN` | Портал → «Разработчикам» → «Другое» → «Входящий вебхук» | Права на **чтение CRM** и **запись задач**. Токен исходящих вебхуков — для проверки входящих событий |
| **Яндекс Директ (!)** | `YANDEX_OAUTH_TOKEN`, `YANDEX_DIRECT_LOGIN` | Приложение: oauth.yandex.ru/client/new · Заявка: кабинет Директа → Инструменты → API | Нужна **одобренная заявка** на доступ к API (не мгновенно). `YANDEX_DIRECT_LOGIN` — только для агентских аккаунтов |
| **Яндекс Метрика** | `YANDEX_METRIKA_COUNTER_ID` (+ тот же `YANDEX_OAUTH_TOKEN`) | Тот же OAuth-кабинет (можно одно приложение с Директом) | Права на счётчик **«Просмотр»** или выше; счётчик привязан к кампаниям Директа |
| **Calltouch** | `CALLTOUCH_CLIENT_API_ID` | Личный кабинет Calltouch → Интеграции / API | API-токен (**clientApiId**) профессиональной версии |
| **МойСклад (!)** | `MOYSKLAD_TOKEN` | МойСклад: профиль сотрудника → «Токен доступа» | Сотрудник с правом **«Видеть себестоимость, цену закупки и прибыль товаров»** — без него поля себестоимости/прибыли в API отсутствуют |
| **Оплаты** | (берутся из Битрикс24 и/или МойСклад) | — | Прямая интеграция с платёжными шлюзами — только если часть оплат не фиксируется в этих системах (согласуется отдельно) |
| **AI-слой (LLM)** | `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` | Провайдер облачного LLM (OpenAI-совместимый API) | Модель и юрисдикция согласуются сторонами (раздел 7 ТЗ). Без ключа AI-инсайты остаются на текущих данных |

## Как включить боевой режим
Через интерфейс: **«Настройка → Интеграции»** → заполнить доступы → «Проверить подключение» →
переключатель источника данных в положение **«Боевые интеграции»** → «Сохранить».

Либо через `.env`:
1. Заполните нужные переменные выше в `.env`.
2. Установите `DATA_SOURCE=real`.
3. Примените и выгрузите:
   ```bash
   docker compose -f docker-compose.prod.yml up -d
   docker compose -f docker-compose.prod.yml exec api python -m app.services.ingest
   ```
Можно подключать интеграции **по одной** — система работает с тем, что настроено;
незаполненные источники просто не дают данных по своей части.

## Критичные действия Заказчика до старта (раздел 8.1 ТЗ)
Отсутствие любого из пунктов останавливает соответствующую часть и сдвигает срок:
- подать заявку на доступ к API **Яндекс Директа** — в первый день;
- выдать доступ к **МойСклад** с правом видеть себестоимость и прибыль;
- определить источник факта оплаты (Битрикс24 / МойСклад / платёжный шлюз);
- подтвердить разметку брендов в МойСклад (папка/группа/атрибут);
- выбрать **модель LLM и юрисдикцию**;
- предоставить рабочий график, производственный календарь и правило определения дублей
  (настраиваются в админ-панели системы).

## Безопасность
- Весь обмен с внешними системами — по **HTTPS/TLS 1.2+** с проверкой сертификата.
- Входящие вебхуки Битрикс24 — только по HTTPS с проверкой токена (`BITRIX24_INBOUND_TOKEN`).
- В образ backend установлены сертификаты **НУЦ Минцифры** (Russian Trusted CA) — для API
  российских сервисов.
- Карточные данные, номера карт, CVV **не обрабатываются и не хранятся** — только факт,
  сумма и статус платежа.
